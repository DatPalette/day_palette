# 配色资产运营整体方案

> ⚠️ 归档说明：本文为早期资产操作方案，当前只保留作历史背景参考。
> 当前跨仓共享的资产生命周期请优先阅读 [`../../../../../daypalette-docs/operations/color-asset-lifecycle.md`](../../../../../daypalette-docs/operations/color-asset-lifecycle.md)。
> `docs/product/strategy/` 目录下的当前主入口请优先阅读 [`../README.md`](../README.md) 与 [`../color-asset-unified-master-plan.md`](../color-asset-unified-master-plan.md)。

> 本文件继续保留为 `day_palette` 仓库内的业务背景与历史规划补充，不再作为跨仓流程真相源。

## 1. 文档目的

本文用于把 DayPalette 当前与后续的配色资产运营方式，收敛成一套能真正落到“项目、界面、文件、发布动作”上的整体方案。

这份方案重点解决两个问题：

1. `BL-BR-08` 缺少明确的运营载体，导致“谁改、在哪改、怎么审、怎么发”不够具体。
2. `BL-BR-10` 虽然已有“本地 JSON / 远端覆盖 / CMS”的分阶段思路，但在当前预算前提下，缺少一个真正可执行的前期路径。

基于当前约束，本文明确采用以下前提：

- 前期**不租服务器、不接云存储、不做后台服务**。
- 前期配色资产仍以**应用内置数据包**为正式发布源。
- 运营入口不再停留在“手改 JSON”或“手改 ArkTS”，而是引入一个**独立的 Web 可视化管理端**。
- 资产修改完成后，由管理端写回结构化数据包，并提交到 GitHub。
- 移动端在需要更新资产时，通过**本地脚本**拉取最新数据包、写回 App 工程资源目录，再随应用版本发布。

---

## 2. 一句话结论

DayPalette 前期的配色资产运营，建议采用这条主路径：

1. 建一个独立的 **Web 管理端前端项目**。
2. 用它可视化管理 `场景 / 基础色 / 配色盘 / 专题合集 / 内容文案`。
3. 管理端把修改写回一组结构化 **JSON 数据包**。
4. 数据包提交到 **GitHub 仓库或仓库内固定目录**。
5. 主应用侧通过一个 **导入脚本**，把这组 JSON 同步到 `entry/src/main/resources/rawfile/palette-data/`。
6. 最终仍按当前方式，**随应用版本发版**。

这意味着：

- 当前阶段的“运营”本质上是 **内容资产编辑与打包流程**，不是线上动态分发系统。
- 当前阶段最需要建设的是 **编辑体验、审核动作、数据一致性**，而不是服务器能力。

---

## 3. 方案定位

## 3.1 它不是什么

这套方案当前不是：

- 线上 CMS
- 实时远端下发系统
- 多人权限后台
- 运营直接改线上生产数据的工具

## 3.2 它是什么

这套方案当前是：

- 一个**本地可运行**的视觉化配色资产管理工作台
- 一个围绕 GitHub 的**内容真相源与版本记录机制**
- 一个把“编辑态资产”转换成“App 可消费数据包”的**前置打包层**

它更像：

- “内容编排工作台 + 数据包生成器”

而不是：

- “在线实时运营后台”

---

## 4. 整体架构

推荐拆成三个实际载体。

### 4.1 载体 A：Web 管理端项目

技术栈按当前建议：

- React
- Vite
- Tailwind CSS
- shadcn/ui

项目职责：

- 可视化展示当前所有配色资产。
- 支持新增、编辑、删除、归档。
- 支持场景、palette、collection 之间的引用关系管理。
- 支持中英文内容文案编辑。
- 支持基础校验、预览和导出数据包。

注意：

- 这是一个**独立项目**，不直接嵌进鸿蒙工程。
- 它的输出物不是线上 API，而是 JSON 文件。

### 4.2 载体 B：配色资产数据包

建议继续沿用当前 App 已存在的结构化数据文件形态，作为正式数据包格式：

- `base-colors.v1.json`
- `palettes.v1.json`
- `collections.v1.json`
- `locale/zh-CN.v1.json`
- `locale/en-US.v1.json`
- 可选 `manifest.local.json`

这组文件是：

- Web 管理端的导出结果
- GitHub 中的版本化资产
- 移动端脚本的导入源
- App 内置资源的直接来源

### 4.3 载体 C：移动端导入脚本

建议在主工程外层或仓库根目录维护一个脚本，例如：

- `scripts/sync-palette-bundle.mjs`

职责：

- 从 GitHub 指定目录读取最新数据包。
- 做基本结构校验。
- 覆盖写入 App 工程中的 `rawfile/palette-data/`。
- 输出变更摘要，便于提交前检查。

这一步不改变 App 运行时逻辑，只改变**发版前的资源输入**。

## 5. 仓库组织建议

当前有两种现实可行路径。

### 5.1 方案 A：与主应用同仓库

建议结构：

```text
day_palette/
  entry/
  docs/
  tools/
    color-asset-admin/
  asset-bundles/
    palette-data/
      base-colors.v1.json
      palettes.v1.json
      collections.v1.json
      locale/
        zh-CN.v1.json
        en-US.v1.json
```

优点：

- 一切都在一个仓库里，最省心。
- 资产变更与 App 代码天然可一起 review。
- 对个人项目最容易维持。

缺点：

- Web 管理端和 App 工程会放在一起，仓库会更重。

### 5.2 方案 B：独立管理端仓库 + App 仓库

建议结构：

- 仓库 1：`day_palette_admin`
  - Web 管理端项目
  - 资产源数据
  - 导出逻辑
- 仓库 2：`day_palette`
  - 鸿蒙 App 工程
  - 导入脚本
  - 内置资源

优点：

- 前后职责更清晰。
- 管理端可以独立演进。

缺点：

- 个人阶段维护心智更高。

### 5.3 当前推荐

当前阶段推荐：

- **先采用方案 A：同仓库管理**。

原因：

- 你是单人维护，核心目标是让运营动作真正落地，而不是把工程边界拆得很漂亮。
- 先把编辑体验、导出结构、导入脚本跑通，比仓库拆分更重要。

## 6. Web 管理端的产品范围

管理端首版建议至少覆盖 5 个主界面。

### 6.1 Dashboard

作用：

- 快速查看当前资产规模和状态。
- 显示待处理草稿、最近修改、已发布 bundle 版本。

建议内容：

- 基础色数量
- palette 数量
- collection 数量
- draft / approved / archived 数量
- 最近修改记录
- 当前导出包版本

### 6.2 Base Color 管理页

作用：

- 管理基础单色资产。

建议支持：

- 色块瀑布或网格展示
- 按 `colorFamily / tone / status / seasonTags` 筛选
- 新增基础色
- 编辑 `hex / 名称 / 标签 / 状态`
- 查看该颜色被哪些 palette 引用

### 6.3 Palette 管理页

作用：

- 管理真正面向用户的三色配色盘。

建议支持：

- palette 卡片式预览
- 按场景、风格、状态、安全等级筛选
- 新增 / 复制 / 编辑 palette
- 可视化选择 `primary / secondary / accent`
- 编辑 `name / desc / hero 文案 / 标签 / safetyLevel / isPro`
- 预览它在移动端 Hero 和列表里的大致呈现

这是首版最核心页面。

### 6.4 Collection 管理页

作用：

- 管理专题或合集。

建议支持：

- 创建 collection
- 从 palette 池里挑选成员
- 拖拽排序
- 设置封面 palette
- 编辑专题名称、说明、标签、状态、是否 Pro

### 6.5 Locale 内容页

作用：

- 管理配色内容文案，而不是 UI 系统文案。

建议支持：

- 场景 label/title 文案
- palette 名称与描述文案
- collection 名称与描述文案
- 中英文对照编辑
- 缺失翻译提示

注意：

- 纯 UI 文案不建议放在首版管理端里一起改。
- 首版聚焦“配色资产相关内容文案”。

## 7. 管理端的数据编辑模型

为了让管理端真正好用，不建议直接把原始 JSON 生硬暴露给界面。

建议拆成两层：

### 7.1 编辑态模型

用于界面编辑，允许携带更多工作字段，例如：

- `isDirty`
- `validationErrors`
- `draftNote`
- `lastEditedBy`
- `lastEditedAt`
- `referenceWarnings`

### 7.2 导出态模型

用于写回 JSON 数据包，只保留 App 运行时真正需要的字段。

这意味着：

- 管理端内部状态可以更丰富。
- 但导出的数据包必须保持克制和稳定。

---

## 8. 数据包导出规则

### 8.1 导出目标目录

若采用同仓库方案，建议导出到：

- `asset-bundles/palette-data/`

### 8.2 导出文件

建议首版固定输出：

- `base-colors.v1.json`
- `palettes.v1.json`
- `collections.v1.json`
- `locale/zh-CN.v1.json`
- `locale/en-US.v1.json`
- `manifest.local.json`

### 8.3 manifest.local.json 建议字段

```json
{
  "schemaVersion": 1,
  "bundleVersion": "2026.04.09.1",
  "exportedAt": "2026-04-09T21:00:00+08:00",
  "counts": {
    "baseColors": 64,
    "palettes": 28,
    "collections": 5
  }
}
```

它当前不是给线上请求用，而是给：

- 导入脚本做检查
- 提交时做人类核对
- 后续如果演进到远端覆盖时复用版本字段

### 8.4 导出校验

导出前至少校验：

1. palette 引用的 colorId 都存在。
2. collection 引用的 paletteId 都存在。
3. `primary / secondary / accent` 不能缺项。
4. `status=published` 的资产必须有完整中文文案。
5. 需要对用户展示的关键资产应有英文或明确允许英文缺省回退。
6. 不允许同一语言下出现完全重复 slug 或稳定命名冲突。

---

## 9. GitHub 在这套方案中的角色

GitHub 当前承担三类职责：

### 9.1 真相源

- 导出的 JSON 数据包最终提交到 GitHub。
- Git 历史天然提供版本记录和回滚能力。

### 9.2 审核界面

- 通过 `git diff` 或 PR diff 查看资产变化。
- 检查某次修改到底改了哪些 palette、文案和专题。

### 9.3 发布中间站

- 移动端导入脚本从 GitHub 读取指定目录或分支中的数据包。
- App 工程同步后再随版本发布。

也就是说，GitHub 前期就是这套运营链路里的“低成本内容中台”。

---

## 10. 移动端导入脚本方案

## 10.1 脚本职责

建议脚本完成以下动作：

1. 定位 GitHub 中的 `asset-bundles/palette-data/`。
2. 读取或拉取最新数据包。
3. 校验关键文件完整性。
4. 覆盖写入：
   - `entry/src/main/resources/rawfile/palette-data/`
5. 输出导入日志：
   - 新增多少基础色
   - 新增或变更多少 palette
   - 新增或变更多少 collection
   - 哪些 locale 文件发生变化

## 10.2 推荐脚本触发方式

建议只在以下时机主动运行：

- 准备发版前
- 批量更新资产后
- 想把管理端最新结果同步进 App 工程时

不建议：

- 每次开发都自动跑
- 在应用运行时动态下载

## 10.3 推荐实现语言

建议使用：

- Node.js 脚本

原因：

- 和 Web 管理端技术栈一致。
- 做 JSON 读写、schema 校验、文件复制最直接。

## 11. 推荐运营流程

建议前期固定成一条简单、可重复的链路。

### 11.1 日常修改流程

1. 打开 Web 管理端。
2. 在界面里修改基础色 / palette / collection / 文案。
3. 在管理端内完成预览与校验。
4. 导出 JSON 数据包。
5. 提交到 GitHub。
6. 在 App 工程执行导入脚本。
7. 检查资源 diff。
8. 随应用版本发版。

### 11.2 审核动作

即使是个人维护，也建议每次导入前过一遍固定清单：

1. 是否有无效引用。
2. 是否有重复资产。
3. 是否有文案空缺。
4. 是否有场景口径漂移。
5. 是否引入过多 experimental 资产。
6. 当前首页四个主场景是否仍然稳定。

### 11.3 发布节奏

前期建议：

- 资产修改并不单独触发线上更新。
- 与 App 常规版本一起发。

这样可以保证：

- 成本低
- 风险低
- 数据与 UI 始终一起验证

## 12. 管理端的视觉与交互原则

你已经明确希望：

- 使用 React + Vite + shadcn + Tailwind CSS
- 设计语言与移动端一致
- 资产展示要足够美观，便于管理

基于这个前提，建议管理端遵守以下原则：

### 12.1 不是传统后台表格系统

不要把它做成只有表格和弹窗的管理后台。

更合适的形态是：

- 介于“策展工作台”和“资产库浏览器”之间

### 12.2 预览优先于字段

对于 palette 和 collection，优先展示：

- 大色块预览
- 真实标题文案
- 场景 / 风格标签
- 当前状态

字段面板放在侧边抽屉或详情页。

### 12.3 页面语言对齐移动端

建议复用移动端当前已经形成的视觉语言：

- 浅底、细边、轻雾化感
- 色卡作为主视觉，不是次要装饰
- 中英文并置时保持气质统一
- 主体信息克制，不做典型企业后台蓝灰风

### 12.4 管理体验的重点

首版管理端最重要的不是权限系统，而是：

- 看得清
- 找得到
- 改得稳
- 导得出

## 13. 与 BL-BR-08 / BL-BR-10 的对应关系

### 13.1 BL-BR-08 现在应该怎么落

`BL-BR-08` 不再抽象地理解为“调研运营工具”，而应具体落为：

- 明确 Web 管理端就是前期运营载体
- 明确 GitHub + 数据包就是前期发布介质
- 明确导出校验 + 导入脚本就是前期发布动作

它的交付物应该变成：

1. 管理端信息架构
2. 资产编辑与审核流程
3. 数据包导出规范
4. 发布前检查清单

### 13.2 BL-BR-10 现在应该怎么落

`BL-BR-10` 不再以前期远端覆盖为主，而是先落成：

- 本地 JSON 结构稳定
- 数据包 manifest 稳定
- GitHub 导出与 App 导入路径稳定

在这个基础上，后续如果要做远端覆盖，再把 GitHub 上的数据包升级为线上拉取源。

也就是说：

- `BL-BR-10` 的第一阶段不是“上云”，而是“把数据包发布链路做对”。

## 14. 分阶段实施建议

### 阶段 A：文档与结构收敛

目标：

- 把数据包目录、导出规范、导入脚本规范写清。

完成定义：

- 文档稳定
- 文件结构冻结第一版

### 阶段 B：管理端原型

目标：

- 先把 Base Color / Palette 管理页做出来。

完成定义：

- 能查看
- 能编辑
- 能本地保存草稿
- 能导出 JSON 数据包

### 阶段 C：导入脚本

目标：

- 把导出的数据包同步进鸿蒙工程资源目录。

完成定义：

- 能导入
- 能校验
- 能输出 diff 摘要

### 阶段 D：首轮真实运营验证

目标：

- 用这条链路真实完成一次 palette 新增或专题更新。

完成定义：

- 管理端修改
- 导出
- GitHub 提交
- App 导入
- 真机验证
- 随版本发布

## 15. 暂定结论

在“不租服务器、不做云存储、仍以内置数据包发版”的前提下，DayPalette 当前最合理的配色资产运营方案是：

- 用一个独立的 Web 可视化管理端承接日常编辑。
- 用 GitHub 承接数据包真相源与版本记录。
- 用移动端导入脚本承接 App 工程资源同步。
- 最终仍随应用版本发版。

这条路径的价值在于：

- 它已经有明确的项目形态。
- 它能落到真实界面和文件。
- 它不依赖额外预算。
- 它为后续远端覆盖保留了升级空间。

对应的工程级技术架构详见：[../../architecture/color-asset-monorepo-architecture.md](../../architecture/color-asset-monorepo-architecture.md)。

因此，后续 `BL-BR-08` 和 `BL-BR-10` 的推进，都应围绕这套“管理端 + GitHub 数据包 + App 导入脚本”的组合来展开，而不是继续停留在抽象的“运营 / 数据更新机制”层面。
