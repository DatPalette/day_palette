# 配色策展工作台 MVP 方案

## 1. 文档定位

本文用于定义 DayPalette 在“主功能已基本成型，接下来进入内容扩容与内容打磨阶段”时，最值得优先建设的内部工具方案。

这份文档不再从“Web 管理端”或“桌面端平台”出发，而是从你当前最真实的工作任务出发：

- 批量查看几十到上百个配色盘。  
- 按场景持续扩充内容。  
- 用肉眼做筛选、比较、淘汰、保留。  
- 避免把预览工作放回模拟器。  
- 在后续仍能平滑接入 GitHub 资产仓库、发布链路与移动端同步。

因此，本文给出的核心建议是：

**先建设一个“预览优先、策展优先、人工筛选优先”的配色策展工作台 MVP。**

---

## 2. 背景判断

## 2.1 当前阶段已经变化

DayPalette 现在面对的主要问题，已经不再是“产品功能够不够完整”，而是：

1. 内容体量即将上升。  
2. 场景数量即将上升。  
3. 每个场景下的候选配色盘会快速增多。  
4. 人工审美判断会成为内容质量的关键环节。

一旦每个场景下开始出现几十到上百个配色盘，“是否存在高效预览与筛选工具”会直接影响内容生产速度。

## 2.2 当前真正的瓶颈

在这个阶段，你真正的瓶颈不是：

- 缺少复杂编辑表单。  
- 缺少完整后台系统。  
- 缺少多人审批流。  

真正的瓶颈是：

1. **如何快速批量预览。**  
2. **如何快速比较。**  
3. **如何快速淘汰不合适的候选。**  
4. **如何把“肉眼判断”沉淀为可复用的运营状态。**

这说明工具的第一优先级应该是“策展工作流”，而不是“复杂管理流”。

---

## 3. 一句话结论

**最适合当前阶段的，不是完整 CMS，不是重桌面平台，而是一个本地使用的“配色策展工作台 MVP”。**

它的第一职责不是录入数据，而是：

- 让你看得快。  
- 让你比得快。  
- 让你筛得快。  
- 让你能把判断结果沉淀下来。  

换句话说：

**先把“看和选”的效率做上来，再补“编和发”的复杂度。**

---

## 4. 产品目标与非目标

## 4.1 MVP 目标

MVP 阶段，这个工作台要解决以下问题：

1. 快速浏览一个场景下的大量配色盘。  
2. 用接近真实产品界面的方式预览配色盘效果。  
3. 快速筛选、标记、收藏、淘汰候选。  
4. 对多个配色盘做并排比较。  
5. 记录人工判断结果，避免完全依赖记忆。  
6. 在最终入选后，把结果导出到正式资产链路。

## 4.2 MVP 非目标

MVP 阶段暂时不做：

1. 多人协作与权限系统。  
2. 复杂审批流。  
3. 在线 CMS。  
4. 运行时动态下发到 App。  
5. 完整通用代码编辑器平台。  
6. 完整 Git 图形客户端。  
7. 复杂插件系统。

---

## 5. 核心产品定义

## 5.1 它是什么

这个工具的正确产品定义应是：

**DayPalette 的配色策展工作台。**

它不是一个传统后台，也不是一个只负责 CRUD 的数据编辑器。

它更像是：

- 一个内部内容策展界面。  
- 一个面向视觉判断的筛选工具。  
- 一个轻量资产工作台。  

## 5.2 它最重要的能力排序

建议按以下优先级理解能力建设顺序：

1. 预览  
2. 筛选  
3. 比较  
4. 标记与状态沉淀  
5. 基础编辑  
6. 导出与发布

如果优先级反过来，很容易做成一个能录入数据、却不适合策展的后台。

---

## 6. MVP 页面范围

MVP 建议至少包含 6 个页面或工作区。

## 6.1 配色盘总览页

目标：

- 批量展示所有配色盘。  
- 支持快速扫描。  
- 支持按场景切换。  

建议内容：

1. 顶部场景切换器。  
2. 搜索框。  
3. 过滤器区域。  
4. 网格卡片流。  
5. 当前结果数量。  
6. 已入选 / 待定 / 淘汰统计。

这一页必须足够快，因为它会成为高频入口。

## 6.2 批量预览页

目标：

- 让你一次看大量候选。  
- 直接看“进产品后的大概样子”。  

建议内容：

1. 每个配色盘都渲染成接近今日页的缩略卡。  
2. 支持调整缩略密度。  
3. 支持只看某一场景。  
4. 支持按状态筛选。  
5. 支持快速标记“保留 / 淘汰 / 待定”。

这是 MVP 的核心页面。

## 6.3 对比页

目标：

- 并排比较多个相似配色盘。  
- 支持肉眼做精细判断。  

建议内容：

1. 同时显示 2 到 6 个配色盘。  
2. 展示主色、辅色、点缀色的角色分布。  
3. 展示标题、副标题、标签等文字叠加效果。  
4. 展示浅底与深底下的可读性。  
5. 支持一键保留一个、淘汰其他。

## 6.4 入选与淘汰管理页

目标：

- 让筛选结果沉淀下来。  
- 避免你每次都重新看。  

建议内容：

1. 按状态查看。  
2. 查看入选理由。  
3. 查看淘汰原因。  
4. 支持恢复淘汰项。  
5. 支持按场景导出最终候选集。

## 6.5 单个配色盘详情页

目标：

- 做更细致的人工判断。  
- 补充必要运营信息。  

建议内容：

1. 配色盘基本信息。  
2. 预览缩略图。  
3. 扩展字段。  
4. 备注。  
5. 审核历史。  
6. 相似配色盘推荐。

## 6.6 发布前检查页

目标：

- 在正式导出前，确认最终资产集处于可发布状态。  

建议内容：

1. 校验错误列表。  
2. 缺失字段列表。  
3. 重复命名提示。  
4. 引用关系问题提示。  
5. 最终 bundle 摘要。  
6. 导出或发布入口。

## 7. 每个配色盘需要新增或强化的运营字段

如果后续要做高频策展，仅靠现有基础字段不够，建议每个配色盘增加一组“运营判断字段”。

## 7.1 必备运营字段

1. `primaryScene`  
用途：主要归属场景，例如 `commute`、`citywalk`、`dating`、`park`。

2. `styleTags`  
用途：风格标签，例如 `urban`、`soft`、`minimal`、`retro-light`。

3. `moodTags`  
用途：情绪标签，例如 `clear`、`relaxed`、`bright`、`quiet`。

4. `safetyLevel`  
用途：区分安全型、表达型、实验型候选。

5. `reviewStatus`  
建议枚举：`candidate / shortlisted / approved / rejected / archived`。

6. `curationScore`  
用途：人工评分，可用 1 到 5 分或 1 到 10 分。

7. `isSelected`  
用途：是否进入当前场景的最终候选集。

8. `rejectionReason`  
用途：记录淘汰原因，例如“层次不清”“过暗”“不够稳定”“与已有方案过近”。

9. `reviewNotes`  
用途：记录肉眼判断和补充意见。

10. `previewVariant`  
用途：指定该配色盘适合哪种预览模板。

## 7.2 推荐扩展字段

1. `visualWeight`  
描述整体视觉重量，例如 `light / balanced / heavy`。

2. `contrastRisk`  
描述潜在可读性风险，例如 `low / medium / high`。

3. `seasonFit`  
描述季节适配度。

4. `heroCopyHint`  
描述适合搭配的文案方向。

这些字段不一定都进入客户端消费层，但对内容筛选很有帮助。

## 8. 预览系统应该如何设计

## 8.1 预览不是简单色块

如果工作台只展示三块颜色，它的价值会很有限。

你真正需要看到的是：

- 这个配色盘进入产品首页后是什么感觉。  
- 标题与副标题压在这个配色上是否舒服。  
- 色块之间是否有层次。  
- 页面整体气质是否成立。  

所以预览必须尽量接近真实产品界面，而不是停留在资产表格层。

## 8.2 建议至少提供 4 类预览模板

### 模板 A：今日页主卡缩略图

用于回答：

- 这个配色盘作为首页主推荐时是否成立。  
- 主标题、标签、按钮是否清楚。  

### 模板 B：列表卡片缩略图

用于回答：

- 这个配色盘在列表中是否足够吸引人。  
- 与其它卡片放在一起时是否容易区分。  

### 模板 C：详情页氛围图

用于回答：

- 这个配色盘是否有独立气质。  
- 是否需要更强故事感文案。  

### 模板 D：对比模式

用于回答：

- 若两个配色盘很接近，谁更值得保留。  
- 哪一个在真实页面结构中更稳。  

## 8.3 每张预览卡建议展示的信息

建议最小展示：

1. 配色盘名称。  
2. 场景标签。  
3. 三色角色条。  
4. 今日页缩略图。  
5. 当前状态。  
6. 人工评分。  
7. 快捷操作按钮。

---

## 9. 为什么不应该继续依赖模拟器

模拟器适合：

- 功能验证。  
- 细节验收。  
- 单个页面效果确认。  

模拟器不适合：

1. 大量候选并排比较。  
2. 快速场景切换。  
3. 批量淘汰。  
4. 内容策展工作流。

因此模拟器在这个阶段应降级为“最终验收工具”，而不是“主要预览工具”。

---

## 10. 推荐的实现形态

## 10.1 先按本地 Web 工具实现

当前更建议先用本地 Web 工具实现这套工作台，而不是直接做重桌面端。

原因：

1. 你当前最需要验证的是“预览策展工作流”本身，而不是桌面壳能力。  
2. 本地 Web 工具足够承载预览、筛选、对比、状态管理。  
3. 这样可以更快迭代 UI。  
4. 如果后续确定需要本地文件系统、GitHub 深集成，再包成桌面端也不晚。

## 10.2 但产品设计要按未来工作台来做

虽然技术实现前期可用本地 Web 工具，但产品设计层面应按“工作台”而不是“网站页面”来组织：

- 强信息密度。  
- 强筛选面板。  
- 强对比能力。  
- 强快捷操作。  
- 强状态沉淀。

这能避免把它做成一个轻飘飘的展示页面。

---

## 11. 推荐的数据链路

建议链路如下：

1. 资产真相源保存在独立资产仓库。  
2. 工作台读取本地或远端同步后的 `source` 数据。  
3. 工作台主要负责预览、筛选、标记和基础编辑。  
4. 入选结果写回资产真相源。  
5. 发布前运行校验。  
6. 构建移动端消费的 bundle。  
7. 由脚本同步到移动端工程。  
8. 最终通过移动端工程构建和验收。

这个链路能把“策展”和“正式发布”分开处理。

---

## 12. MVP 分阶段建议

## 12.1 阶段一：只做看、筛、标

先实现：

1. 总览页。  
2. 批量预览页。  
3. 对比页。  
4. 基础筛选。  
5. 状态标记。  
6. 备注记录。

这一阶段的目标只有一个：

**让你能高效处理几十到上百个候选配色盘。**

## 12.2 阶段二：补基础编辑

再实现：

1. 配色盘详情页。  
2. 基础字段编辑。  
3. 原始 JSON 编辑入口。  
4. 批量标签修改。

## 12.3 阶段三：补发布闭环

最后实现：

1. 校验面板。  
2. bundle 构建。  
3. GitHub 提交或导出。  
4. 移动端同步脚本衔接。

这个顺序能确保最早解决你的核心痛点，而不是先堆底层能力。

---

## 13. 成功标准

这套 MVP 是否成功，不看它是否像一个成熟后台，而看下面几个指标：

1. 你能否在一个页面内快速扫完 50 到 100 个配色盘。  
2. 你能否在 10 分钟内完成一次场景内的初筛。  
3. 你能否很快回忆起为什么某个候选被淘汰。  
4. 你能否在不打开模拟器的前提下完成大部分内容判断。  
5. 你能否把最终入选结果顺畅推进到移动端资源链路。

如果这几件事做到了，这个 MVP 就是成功的。

---

## 14. 最终建议

如果基于你当前“主功能已成型，接下来进入内容大规模扩充与人工审美筛选阶段”的现实，只给一个建议，那么我会建议：

**先做一个预览优先的配色策展工作台 MVP。**

它不需要一开始就成为完整桌面端平台，也不需要一开始就成为完整 CMS。

它首先应该解决的，是下面四件事：

1. 看得快。  
2. 比得快。  
3. 筛得快。  
4. 记得住。  

等这套策展工作流跑顺以后，再决定是否把它包成桌面端、是否深接 GitHub、是否扩展成更完整的资产工作台。

也就是说：

**现在最值得投入的，不是“管理端架构”，而是“内容筛选效率”。**
