# 桌面端配色资产工作台可行性方案

## 1. 文档目的

本文用于分析 DayPalette 是否应把原先设想中的“本地 Web 管理端 + monorepo”方案，调整为一个**独立维护的桌面端配色资产工作台**。

本文重点回答以下问题：

1. 这个方向是否可行。  
2. GitHub 是否适合作为个人运营阶段的“远端对象存储 + 版本仓库”。  
3. 桌面端发起本地服务、编辑数据、再同步到移动端工程，是否是合理链路。  
4. 桌面端内集成代码编辑器、支持字段扩展，是否值得在前期就纳入。  
5. 如果要做，推荐采用什么架构与分阶段策略。

---

## 2. 背景与问题重述

此前方案的核心思路是：

- 做一个本地 Web 管理端。  
- 用 monorepo 把管理端、配色资产、schema、CLI、移动端工程放在一起。  
- 通过本地 bridge 或 CLI，把编辑后的资产同步到客户端工程。  

新的想法则是：

1. 直接做一个**桌面端应用**，不再优先做浏览器中的管理端。  
2. 桌面端应用可发起**本地服务**，承担本地 API、预览、校验、导入导出等职责。  
3. 编辑完成后，桌面端可调用 GitHub API，把资产保存到某个独立仓库中，把 GitHub 当作个人运营阶段的远端持久化存储。  
4. 移动端项目中保留一条“拉取最新配色资产”的脚本链路，用于把远端仓库中的正式资产同步回当前 App。  
5. 桌面端内可集成一个代码编辑器，用于处理 JSON/YAML/自定义字段等扩展场景。  
6. 该桌面端项目独立维护，不强依赖 monorepo。

这条思路本质上是把“资产运营工具”从“本地 Web 工具”升级为“本地桌面工作台”。

---

## 3. 一句话结论

**可行，而且从你当前“单人运营 + 强结构化资产 + 需要可扩展编辑能力”的阶段判断，这条路比 Web 管理端更贴近真实使用方式。**

但需要明确三点：

1. 它更像一个**内容工作台**，而不是一个轻后台。  
2. GitHub 适合做**版本化资产仓库**，但不适合把它理解成真正意义上的数据库。  
3. 前期不应一上来就把“桌面端 + 本地服务 + 编辑器扩展 + schema 系统 + 移动端拉取链路”一次性做满，而应按阶段拆开。

换句话说：

- **方向成立。**  
- **前期值得做。**  
- **但要按“先工作流闭环，再补高级能力”的顺序推进。**

---

## 4. 为什么桌面端方案更贴近你的真实场景

## 4.1 你的核心问题不是“给别人一个后台”

你当前面对的问题不是多角色协作，也不是要快速上线一个给运营同学使用的 CMS。

你的真实需求更像是：

- 需要一个自己长期使用的资产工作台。  
- 需要同时做“表单编辑 + 结构校验 + 原始文本编辑 + 版本管理”。  
- 需要在一个本地可信环境里处理数据。  
- 需要在未来支持字段扩展，而不是被首版表单结构锁死。  

这种场景下，桌面端天然比浏览器更顺手，因为它更容易承接：

- 本地文件系统访问。  
- 本地缓存与草稿。  
- 本地服务进程。  
- 集成代码编辑器。  
- 调用 git / GitHub API。  
- 导入导出和批量处理。

## 4.2 你的编辑对象本质上是“结构化内容资产”

配色资产不是单纯表单数据，它有明显的“半结构化内容”特征：

- 固定字段，如 `id`、`hex`、`tags`、`status`。  
- 可扩展字段，如未来新增的运营标签、实验性元数据、主题附加信息。  
- 对引用关系敏感，如 `Base Color -> Palette -> Collection`。  
- 对 schema 校验敏感，如唯一性、枚举合法性、引用完整性。  

这意味着后续一定会出现两类编辑需求并存：

1. 可视化表单编辑。  
2. 原始文本或结构化代码编辑。

桌面端把这两种模式放在同一个工作台里，更自然。

## 4.3 你希望它独立维护

这个判断是合理的。

如果桌面端项目独立维护：

- 它的依赖、发布节奏、技术栈可以完全围绕“资产运营工具”优化。  
- 不会污染 Harmony 工程的工具链。  
- 后续如果桌面端形态变化，也不会强行拖动移动端仓库结构。  

这比为了共享类型而强上 monorepo，更符合你当前的维护方式。

---

## 5. 可行性分析

## 5.1 技术可行性

结论：**高。**

原因：

1. 桌面端应用完全可以发起本地 HTTP 服务或本地进程服务。  
2. 桌面端应用可以直接访问本地文件系统，管理草稿、缓存和导出结果。  
3. 调用 GitHub API 或直接执行 git 命令，都属于成熟路径。  
4. 集成 Monaco Editor 或类似编辑器，在桌面端也非常成熟。  
5. 从远端仓库拉取 JSON 资产，再同步到移动端工程，也是一条简单可控的自动化链路。

你真正需要解决的不是“能不能做”，而是“哪些能力必须前期做，哪些应该延后”。

## 5.2 产品可行性

结论：**高。**

这个方向符合 DayPalette 当前阶段的产品现实：

- 资产主理人基本就是你自己。  
- 内容规模还不算大，但结构要求已经开始变复杂。  
- 比起多人协同审批，更重要的是先把资产录入、校验、预览、存档、同步闭环建立起来。  

桌面端工作台能把“内容策展工具”做得更像生产工具，而不是为了适配浏览器而被迫拆成多个零碎模块。

## 5.3 维护可行性

结论：**中高。**

优点：

- 项目边界清晰。  
- 本地工具链独立。  
- 适合单人持续演进。  

成本点：

- 需要同时维护桌面端项目和移动端项目。  
- 需要设计稳定的数据 schema 和导入导出协议。  
- 一旦桌面端承担过多职责，复杂度会快速上升。

所以关键不是“独立项目是否可维护”，而是“必须限制它前期职责”。

## 6. GitHub 作为远端对象存储的可行性

## 6.1 适合做什么

GitHub 很适合承担以下角色：

1. **配色资产正式仓库**。  
2. **版本历史记录系统**。  
3. **跨机器恢复来源**。  
4. **轻量远端备份**。  
5. **个人运营阶段的发布源**。

对于当前阶段，GitHub 的价值主要在于：

- 有版本历史。  
- 有差异对比。  
- 有远端备份。  
- 有成熟 API。  
- 不需要自建服务器。

## 6.2 不适合做什么

GitHub 不适合被当成：

1. 高频实时数据库。  
2. 多人并发编辑协调层。  
3. 细粒度权限运营后台。  
4. 运行时客户端动态查询接口。

因此这里更准确的定义不是“GitHub 对象存储”，而是：

**GitHub 作为版本化资产仓库与远端发布源。**

这个表述更准确，也更贴近你的真实用途。

## 6.3 推荐保存方式

推荐不要只把一整份大 JSON 直接覆盖上传，而是按以下思路组织：

1. 远端独立仓库存放 `source/`、`bundle/`、`schema/`、`manifest.json`。  
2. `source/` 存编辑态真相源。  
3. `bundle/` 存移动端消费的发布态产物。  
4. `manifest.json` 记录 `bundleVersion`、更新时间、变更摘要。  
5. 桌面端发布时尽量走一次完整的“校验 -> 构建 bundle -> 提交远端”。

这样做的好处是：

- 编辑态和发布态分离。  
- 移动端不必理解所有编辑态字段。  
- 后续字段扩展不会立即污染客户端消费层。

## 7. 本地服务是否有必要

## 7.1 可以有，但前期不一定必须有

你提到“桌面端应用可发起本地服务”，这本身没有问题。

但从架构职责上看，本地服务有两种完全不同的使用方式：

### 方式 A：桌面端内部直接调用本地模块

也就是：

- UI 层直接调用本地 Node/Rust/Electron 主进程能力。  
- 不通过 HTTP API。  
- 校验、导出、GitHub 提交都在桌面应用内部完成。

这是**前期更推荐**的方式，因为链路更短、调试更简单。

### 方式 B：桌面端先起一个本地服务，再由 UI 调它

也就是：

- 本地服务暴露 `validate`、`publish`、`preview`、`pull-latest` 等接口。  
- UI 相当于一个桌面壳内的前端客户端。  

这个方式更适合以下场景：

- 未来想把同一套能力同时给 Web 管理端复用。  
- 未来会有插件系统或脚本系统。  
- 未来要把“桌面 UI”和“资产处理引擎”做成分层产品。

## 7.2 当前推荐判断

**前期不必为了“架构好看”强行起本地服务。**

更建议：

1. 先把桌面端做成一个本地应用。  
2. 先把资产校验、打包、提交 GitHub 的能力封装成应用内部服务模块。  
3. 只有在你明确需要对外暴露 API 或支持多入口时，再抽出本地 HTTP 服务层。

否则很容易出现一个问题：

- 你本来只是想做一个自己用的生产工具。  
- 结果前期先多维护了一套本地服务协议、错误码、接口层、进程通信层。  

这会徒增复杂度。

---

## 8. 集成代码编辑器的必要性

## 8.1 这个能力是合理的

你提到希望桌面端内集成一个代码编辑器，以便未来扩展字段和扩展数据格式。

这个判断是对的，因为配色资产后续大概率会出现：

- 表单还没覆盖的新字段。  
- 某些需要批量修改的 JSON 片段。  
- 某些实验性字段暂时不想进入正式 UI 表单。  
- schema 演进期的兼容编辑需求。

如果完全没有原始编辑模式，桌面端会很快变得“只能处理设计时预设过的字段”，扩展性会不足。

## 8.2 但不要把它做成完整 IDE

前期应避免把它演进成“桌面版 VS Code 替代品”。

推荐只做以下能力：

1. 原始 JSON/YAML 文本编辑。  
2. schema 驱动的错误提示。  
3. 基础自动补全。  
4. 只读 diff 预览。  
5. 发布前校验结果定位。

不建议前期就做：

1. 多标签复杂工程编辑器。  
2. 通用插件市场。  
3. 任意脚本执行系统。  
4. 完整 Git 图形客户端。

你的目标应该是“资产编辑器 + 结构化文本后门”，不是“通用开发环境”。

---

## 9. 与原 monorepo 方案的对比

## 9.1 原方案的优点

原方案的好处在于：

- 类型与 schema 共享更自然。  
- 一个仓库里就能看完管理端、工具链和客户端。  
- 若未来做多人协作式 Web 管理端，更容易演进。

## 9.2 原方案的不足

对于你当前阶段，原方案的问题也很明显：

- 它本质上仍是“为了浏览器而设计”的编辑工具。  
- 对本地文件系统、Git、导入导出、原始编辑的承接不如桌面端自然。  
- 如果最终主要使用者始终是你自己，monorepo 的收益没有想象中大。  
- Harmony 工程与 Node 工具链共仓维护，心智负担会更高。

## 9.3 新方案的优点

桌面端方案的核心优势在于：

1. 更接近“本地内容工作台”。  
2. 更方便整合文件系统、编辑器、GitHub 提交、预览、校验。  
3. 可以把移动端项目与运营工具项目彻底分开。  
4. 更适合单人长期运营和渐进式演化。

## 9.4 新方案的代价

桌面端方案也有明确代价：

1. 跨项目共享类型和 schema，需要通过 npm 包、Git 子模块、复制脚本或独立 schema 仓库来解决。  
2. 若未来想做多人在线协作，桌面端路线不如 Web 路线自然。  
3. 桌面端一旦做重，复杂度并不会低于一个小型后台。

## 9.5 当前推荐取舍

对于你现在的阶段，更推荐：

**优先采用“独立桌面端工作台 + 独立资产仓库 + 移动端拉取脚本”的路线。**

原因不是它更先进，而是它更符合你当下的真实工作流。

---

## 10. 推荐的目标架构

建议拆成三个独立仓库，而不是一个 monorepo。

## 10.1 仓库一：桌面端工作台

建议职责：

- 资产浏览与编辑。  
- schema 校验。  
- bundle 构建。  
- GitHub 发布。  
- 本地草稿管理。  
- 预览与 diff。

建议内部模块：

```text
desktop-workbench/
  src/
    ui/
    editor/
    preview/
    services/
      asset-repo/
      validator/
      bundler/
      github-sync/
    schemas/
    types/
```

## 10.2 仓库二：远端配色资产仓库

建议职责：

- 承载编辑态资产真相源。  
- 承载发布态 bundle。  
- 承载 manifest 和版本记录。  
- 承载必要 schema 快照。

建议结构：

```text
color-assets-repo/
  source/
    base-colors.json
    palettes.json
    collections.json
    locale/
  bundle/
    current/
      manifest.json
      base-colors.json
      palettes.json
      collections.json
      locale/
  schema/
  CHANGELOG.md
```

## 10.3 仓库三：移动端 App 仓库

建议职责：

- 保持当前 HarmonyOS App 工程独立。  
- 通过脚本拉取 `bundle/current/`。  
- 把拉取后的数据写入客户端约定目录。  
- 客户端只消费发布态 JSON。

这样分仓后，职责会很清晰：

- 桌面端负责生产。  
- 资产仓库负责保存。  
- 移动端负责消费。

---

## 11. 推荐的数据流

建议的数据流如下：

1. 在桌面端打开本地草稿工作区。  
2. 通过表单或原始编辑器修改 `source/` 数据。  
3. 本地运行 schema 校验、引用校验、命名校验。  
4. 本地生成给移动端消费的 `bundle/current/`。  
5. 生成发布摘要与 diff。  
6. 用户确认后，提交到 GitHub 资产仓库。  
7. 移动端项目通过脚本拉取最新 `bundle/current/`。  
8. 将 bundle 写入 Harmony 工程的资源目录。  
9. App 在构建时使用最新内置资产。

这个链路比“桌面端直接改移动端工程文件”更干净，因为中间多了一个远端正式仓库，具备版本化和恢复能力。

---

## 12. 对移动端项目的影响

## 12.1 影响范围可控

这个方案不会要求移动端项目改成动态远端拉取。

移动端仍然可以坚持：

- 只读取本地内置 JSON。  
- 随 App 版本发布。  
- 不把运行时内容同步逻辑带进客户端。

这点很重要，因为它避免了：

- 审核风险上升。  
- 客户端状态不一致。  
- 远端异常影响 App 启动。

## 12.2 你需要补的只是一个同步脚本

移动端仓库中只需额外维护一条脚本链路，例如：

1. 拉取 GitHub 资产仓库最新 bundle。  
2. 覆盖或更新 `entry/src/main/resources/rawfile/...`。  
3. 生成必要 manifest。  
4. 做一次基础校验。

这比在移动端工程内塞进编辑逻辑要干净很多。

## 13. 前期最值得做的 MVP

如果采用这条路线，前期最小可用版本建议只做下面这些：

## 13.1 桌面端 MVP 范围

1. 浏览 `Base Color / Palette / Collection`。  
2. 表单编辑基础字段。  
3. 原始 JSON 编辑模式。  
4. 本地校验。  
5. 构建 `bundle/current/`。  
6. 一键提交到 GitHub 资产仓库。  
7. 查看发布摘要。

## 13.2 暂时不要做的能力

1. 多人协作。  
2. 在线账号系统。  
3. 复杂审批流。  
4. 插件系统。  
5. 通用脚本执行器。  
6. 运行时下发到 App。  
7. 完整可视化 Git 客户端。

只要先把这条闭环做出来，你的资产运营就已经从“手改文件”升级成“有生产工具”。

## 14. 风险与注意点

## 14.1 最大风险不是技术，而是职责膨胀

桌面端最容易失控的地方是：

- 一开始只是想做资产编辑器。  
- 后来逐步塞进发布器、预览器、脚本平台、Git 客户端、规则引擎。  
- 最后变成一个过重的内部平台。

因此必须持续守住边界：

**它首先是资产工作台，其次才是工具平台。**

## 14.2 Schema 治理要尽早做

既然你明确提到将来要扩展字段，那么必须从一开始就约束：

1. 哪些字段属于发布态。  
2. 哪些字段只属于编辑态。  
3. 哪些字段允许实验扩展。  
4. 哪些字段变更会影响客户端解析。

否则桌面端编辑越自由，移动端消费层越容易失控。

## 14.3 GitHub 凭证与权限要谨慎

如果桌面端直接调用 GitHub API，需要注意：

- Token 存储方式。  
- 仓库权限最小化。  
- 发布分支策略。  
- 错误回滚机制。

前期建议至少做到：

1. 使用最小权限 token。  
2. 只写指定资产仓库。  
3. 每次发布生成明确 commit message。  
4. 支持失败后保留本地草稿，不直接覆盖。

---

## 15. 推荐实施顺序

建议按四个阶段推进。

## 15.1 阶段一：先定义资产仓库协议

先明确：

- `source/` 怎么组织。  
- `bundle/` 怎么组织。  
- `manifest` 怎么定义。  
- schema 如何约束。  
- 移动端最终消费哪些字段。

这一阶段先把数据协议定清楚，比先画桌面端 UI 更重要。

## 15.2 阶段二：做桌面端最小编辑器

先实现：

- 浏览。  
- 编辑。  
- 校验。  
- 构建 bundle。  

此时甚至可以先不接 GitHub，只在本地工作区跑通。

## 15.3 阶段三：接入 GitHub 发布能力

实现：

- 读取资产仓库。  
- 提交变更。  
- 查看 diff 与发布摘要。  
- 生成版本记录。

## 15.4 阶段四：补移动端拉取脚本

最后再在移动端仓库补：

- 拉取最新 bundle。  
- 覆盖资源目录。  
- 本地校验。  
- 供你手动构建 App。

这个顺序能保证每一步都能独立验证，不会一开始就同时维护三端联动。

## 16. 最终建议

如果只给一个建议，我会这样定：

**把“配色资产运营工具”重新定义为“独立桌面端资产工作台”，并把 GitHub 定义为远端版本化资产仓库；移动端项目继续只消费发布态 bundle，通过脚本手动同步。**

对应的判断是：

1. 这条路比本地 Web 管理端更符合你的真实使用方式。  
2. 它比 monorepo 更适合当前单人维护。  
3. 它能更自然地承接本地文件、GitHub、原始编辑器和字段扩展。  
4. 真正需要警惕的不是技术不可行，而是前期把工作台做得过重。

所以最稳妥的方向不是“立刻做一个很全的桌面平台”，而是：

**先做一个能完成“编辑 -> 校验 -> 构建 -> 发布到 GitHub”闭环的桌面端 MVP。**
