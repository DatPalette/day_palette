### BL-BR-10 · 配色数据更新机制设计（内置 / 远端覆盖 / CMS）

**目标**

- 明确 DayPalette 的配色资产未来如何更新，避免“每次调 palette 都必须重新发版”成为长期阻塞。

**方案设计**

- 采用分阶段评估：
  - `阶段 0`：完全内置，继续使用随应用版本发布的数据。
  - `阶段 1`：内置基础库 + 远端 JSON 覆盖，用于低成本更新配色盘与专题。
  - `阶段 2`：仅当多人协作与高频内容更新成立时，再考虑 CMS。
- 当前建议补充为：
  - `阶段 1 验证版`：可先用 `GitHub Pages` 或免费静态托管验证远端覆盖链路。
  - `阶段 1 正式低成本版`：优先使用**对象存储直出静态 JSON**，而不是先做服务端系统。
- 方案文档需明确：缓存、签名或版本字段、失败回退、离线降级、兼容老版本客户端的边界。
- 与当前 `LocaleData.ets` 的真实实现对照，产出“从硬编码迁移到文件化资源”的过渡路线。
- 低成本技术方案与部署对比详见 [../../architecture/low-cost-remote-json-stage1-plan.md](../../architecture/low-cost-remote-json-stage1-plan.md)。

**交付物**

- 一份分阶段选型结论。
- 一份真实数据文件路径与加载方式草案。
- 一份低成本可落地方案对比表（`GitHub Pages / 对象存储 / 静态托管 / 云函数`）。
- 一份远端覆盖的风险清单与降级策略。

### BL-BUG-01 · TopBar 日期与系统日期不同步修复

**目标**

- 保证 TopBar 显示日期始终与系统当前日期一致，不因跨天、前后台切换、系统时区变化或语言切换而滞后。

**方案设计**

- 先确认当前 TopBar 日期字符串的真实来源，是直接读系统时间、读缓存、还是复用 ViewModel 中的今日快照状态。
- 检查以下触发链路是否都会刷新日期：应用冷启动、应用回前台、跨午夜、系统时区变化、系统语言变化。
- 若当前日期依赖“今日配色快照”而不是独立的日历日边界，应把“展示日期”和“配色快照日期”拆开，避免 UI 错把业务缓存当系统时间。
- 修复后要确认 TopBar、Hero 副标题、昨日功能判定三者对“今天/昨天”的定义保持一致。

**交付物**

- 一份问题定位结论。
- 一份修复方案或实际修复结果。
- 一份覆盖冷启动、回前台、跨天、时区切换的验证清单。

**当前进展（2026-04-07）**

- 已定位根因：TopBar 直接使用 `LocaleData` 中的静态 `ui.date` 示例文案，未绑定系统当前日期。
- 已改为由 ViewModel 基于系统当前日历日动态格式化日期字符串，不再依赖静态文案。
- 已补两条刷新链路：应用回前台时刷新日期；应用保持前台跨午夜时，自动在下一次本地午夜后刷新。
- 待用户在 IDE 中实际运行确认时区切换场景；当前已完成代码侧修复与文件级检查。


### BL-UX-01 · 精调能力升级与交互方案设计

**目标**

- 为精调功能制定一版可执行的升级方案，让用户既能更自由地改色，又不会因为交互过重而失去 DayPalette 的轻量感。

**方案设计**

- 先明确能力边界：第一版升级建议允许用户分别修改 `primary / secondary / accent` 三个角色颜色，但不开放无限自由编辑的复杂面板作为默认主路径。
- 用户可改的内容建议分三层：
  - `层 1`：直接替换当前三格中的任一角色颜色。
  - `层 2`：基于当前角色给出安全候选色，优先从已审核 `BaseColor / Palette` 资产中选，不鼓励直接裸输任意 HEX 作为主路径。
  - `层 3`：保留进阶入口处理手动 HEX / 最近使用 / 恢复默认，但放在二级层，不抢主流程。
- 交互形式建议优先评估“底部 Sheet + 角色分段切换 + 候选色网格”的结构，而不是三个输入框直改：
  - 进入精调后先看到当前三色预览与 `主色 / 辅色 / 点缀色` 分段选择。
  - 选中某一角色后，下方展示该角色的安全候选色网格，以及少量按场景过滤后的推荐色。
  - 顶部保留“恢复当前套组”“撤销上一步”“应用”三种清晰动作，减少误操作。
- 状态流转建议：
  - 用户进入 Sheet 时以当前 palette 为基线。
  - 在 Sheet 内的改动先作为临时预览，可实时映射 Hero。
  - 用户关闭时若有未提交改动，明确区分“应用修改 / 放弃修改”。
  - 若后续重新接回扩展搭配，精调也要能识别“当前基线来自推荐结果还是原始 palette”。
- 需要单独说明不做什么：
  - 不把精调做成完整专业调色板工具。
  - 不在首版默认暴露过多高级参数，如饱和度滑杆、明度曲线、色轮自由选点。

**交付物**

- 一份精调升级交互草案。
- 一份“用户可修改颜色范围”定义清单。
- 一份状态流转说明：进入、预览、撤销、恢复、应用、关闭。
- 一份后续实现拆分建议（低风险版 / 完整版）。

**当前进展（2026-04-08）**

- 已完成首版交互原型：三角色切换 + 推荐色候选 + 手动 HEX + 撤销 + 恢复套组色 + 应用。
- 当前弹层实现已从自绘遮罩改为 ArkUI 系统 `bindSheet`，用于改善蒙层和开合动画的一致性。
- 已完成第二轮界面收敛：默认隐藏高级输入，补齐次级操作按钮版式，并统一主界面与精调面板的选中态语言。
- 已补应用结果反馈：精调应用成功后按“仍为微调态 / 已回到套组基线”分别给出 toast；首页 palette 卡的常驻微调标识已取消，避免干扰原始卡片布局与色条区域。
