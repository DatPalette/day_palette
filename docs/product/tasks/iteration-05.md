- 本迭代重点是**策略落地、数据方案和文案收敛**，不是立即扩充大量新套组。

## 每项任务的方案设计

### BL-BR-10 · 配色数据更新机制设计（内置 / 远端覆盖 / CMS）

**目标**

- 明确 DayPalette 的配色资产未来如何更新，避免“每次调 palette 都必须重新发版”成为长期阻塞。

**方案设计**

- 采用分阶段评估：
  - `阶段 0`：完全内置，继续使用随应用版本发布的数据。
  - `阶段 1`：内置基础库 + 远端 JSON 覆盖，用于低成本更新配色盘与专题。
  - `阶段 2`：仅当多人协作与高频内容更新成立时，再考虑 CMS。
- 当前建议补充为：
  - `阶段 1 验证版`：可先用 `GitHub Pages` 或免费静态托管验证远端覆盖链路。
  - `阶段 1 正式低成本版`：优先使用**对象存储直出静态 JSON**，而不是先做服务端系统。
- 方案文档需明确：缓存、签名或版本字段、失败回退、离线降级、兼容老版本客户端的边界。
- 与当前 `LocaleData.ets` 的真实实现对照，产出“从硬编码迁移到文件化资源”的过渡路线。
- 低成本技术方案与部署对比详见 [../../architecture/low-cost-remote-json-stage1-plan.md](../../architecture/low-cost-remote-json-stage1-plan.md)。

**交付物**

- 一份分阶段选型结论。
- 一份真实数据文件路径与加载方式草案。
- 一份低成本可落地方案对比表（`GitHub Pages / 对象存储 / 静态托管 / 云函数`）。
- 一份远端覆盖的风险清单与降级策略。


### BL-BR-08 · 运营侧内容管理方案调研与选型

**目标**

- 在不引入重 CMS 的前提下，形成一套主理人可长期维护的配色资产工作流。

**方案设计**

- 先把“编辑态 / 发布态 / 审核态”三段流程写清，再决定是否需要工具。
- 编辑态优先看结构化表格；发布态优先看仓库内 JSON；工具选型只作为后续增强项。
- 审核口径需覆盖：命名一致性、场景适配、色彩风险、资产重复度。

**交付物**

- 一份低成本维护流程说明。
- 一份工具选型对比表。
- 一份审核清单模板。

**当前进展（2026-04-07）**

- 已确定“代码内规则引擎 + `rawfile` 策略 JSON”作为当前最小可维护方案。
- 运营当前可直接维护的核心文件为 `entry/src/main/resources/rawfile/smartmatch/strategy.v1.json`。
- 已补首版运营指导文档：[../strategy/extended-pairing-ops-guide.md](../strategy/extended-pairing-ops-guide.md)，用于说明可修改字段、审核边界与发布动作。
- 后续仍需补齐工具选型对比表与正式审核清单模板。

### BL-BR-03 · 精调：「智能配」主路径 + 可展开完整微调
