## 范围边界

- 本迭代重点是**发布准备 + 设备适配 + 品牌视觉入口**，不是继续扩展新功能。
- 若自检中发现问题涉及较大产品变更，应先记录为新 Backlog，而不是在本轮顺手扩需求。
- 本迭代优先处理**依赖链路短、能立即完成**的事项；需要等待商业化、完整商店配置或大面积功能闭环后才能判断的问题，默认回到 Backlog 跟踪。
- 适配工作以**今日页主路径、设置面板、导出/分享、Form 相关入口**为优先，不追求一次性覆盖所有未来页面。
- 图标设计以当前产品定位“高级、克制、编辑感”为约束，不引入卡通化或过度装饰风格。


## 本轮不做 / 回到 Backlog

- **商业化闭环**：IAP、恢复购买、Pro 权益锁态、商店商业化说明，继续由 [Backlog.md](./Backlog.md) 中 `BL-PRD-01～04` 跟踪。
- **依赖正式提审资料后才能定稿的事项**：如最终商店商品页文案、商业化截图、付费权益细则，不作为本轮整改阻塞项。
- **需要完整宽屏实现后才能给出结论的发布项**：平板与宽屏最终截图留到 `BL-ADAPT-01 / 02` 产出后再做验收，不在 BL-REL-01 首轮自检阶段强行关闭。

## 每项任务的方案设计

### BL-REL-01 · HarmonyOS 上架规范自检与整改

**目标**

- 在真正提审前，把会导致驳回、误导或素材不合规的问题提前收敛掉。

**方案设计**

- 以 [../../release/test-release-checklist.md](../../release/test-release-checklist.md) 为项目内检查基线，但本轮只处理**短依赖链、可立即落地**的维度：应用信息、权限说明、隐私政策、截图素材清单、图标与名称一致性。
- 将检查项分为三类：
  - `本轮立即整改`：当前就能完成，且越早修越不容易扩散的问题。
  - `本轮观察`：需要继续留意，但不应阻塞当前迭代推进的问题。
  - `回到 Backlog`：依赖商业化、商店配置或更大范围实现闭环的问题。
- 自检输出应形成一份可复查的问题清单，而不是只给口头结论；整改完成后再回写清单状态。

**建议检查维度**

- 应用名、包名、版本号、图标、截图、简介是否一致。
- 权限申请理由是否真实对应保存/分享路径。
- 隐私政策、权限说明、相册写入行为是否对齐。
- `Debug`/测试入口、沙箱账号信息、测试开关是否在 release 可见。
- 若本次版本**不含商业化闭环**，则只检查“是否误导用户”，不要求在本轮完成 IAP 能力本身。

**交付物**

- 一份上架自检记录。
- 一份整改清单与处理结果。
- 若需要，补充或修订发布文档与 PRD 文案。

**当前进展（2026-04-07）**

- 已建立首轮自检记录：[../../release/release-self-audit-iteration-04.md](../../release/release-self-audit-iteration-04.md)。
- 已识别的本轮短链路整改项包括：基础信息占位值、隐私政策缺失、发布文档旧路径、上架素材未建档。

### BL-ADAPT-01 · 手机 / 平板多尺寸自适应收敛

**目标**

- 让今日页在手机与平板上都保持“高级编辑感”，而不是简单等比放大。

**方案设计**

- 先建立尺寸分层，而不是逐机型打补丁。建议至少分为：
  - `Compact`：常规手机窄屏。
  - `Medium`：大手机 / 小平板竖屏。
  - `Expanded`：平板与更宽窗口。
- 以布局令牌驱动适配：页面水平留白、Hero 最大宽度、顶部栏高度、场合区与精选配色盘的列表宽度、底部操作区宽度，不允许把断点逻辑散落在多个组件里。
- 优先检查这些页面结构：
  - TopBar 在不同宽度下是否还能保持标题、设置按钮、微缩预览的稳定关系。
  - Hero 是否出现过宽、过矮或色卡层叠松散的问题。
  - 场合横滑与精选配色盘在平板上是否仍然显得过窄。
  - 设置面板在平板上是否仍应占满全屏，还是转为受控宽度侧栏。
  - 底部保存 / 分享按钮在大屏上是否需要限制最大宽度，避免过长导致廉价感。

**建议实现策略**

- 新增统一的窗口尺寸分类或断点 helper，由页面层读取后下发给关键组件。
- 在关键组件中优先使用“最大宽度 + 自适应居中”策略，而不是所有内容跟随屏幕无限拉宽。
- 将手机与平板共用同一套视觉语言，只改变容器宽度、间距和布局结构，不改变核心组件语义。

**交付物**

- 尺寸断点定义。
- 今日页核心组件的适配规则表。
- 至少一轮手机 / 平板主要尺寸验收结论。


### BL-ADAPT-02 · 大尺寸宽屏布局方案设计与落地

**目标**

- 在宽屏平板上提供真正适配大画幅的版式，而不是手机版纵向长卷在中间悬一列。

**方案设计**

- 宽屏设备建议采用**双栏 / 偏编辑版式**：
  - 左栏承载 TopBar、Hero 与色值信息，作为主视觉区。
  - 右栏承载场合选择、精选配色盘、动作区与设置入口相关内容，形成操作区。
- 若宽度进一步增大，可考虑让右栏的精选配色盘从单行横滑改为更具陈列感的网格或双列卡片，但仍保持“精选”而非工具表格的气质。
- 设置面板在宽屏场景下可优先评估“右侧固定宽度面板”而不是全屏覆盖，以减少大屏切换时的空间浪费。
- 宽屏布局必须保留产品的留白、重心与材质层次，避免为了利用空间而堆满内容。

**建议验收点**

- 宽屏下 Hero 仍然是视觉主角，而不是被右栏内容抢走重心。
- 右栏操作密度提升后，仍然清晰可点、不显拥挤。
- 横竖屏切换或窗口尺寸变化时，布局切换不出现明显跳变和状态错位。

**交付物**

- 一份宽屏布局草案说明。
- 宽屏断点下的页面结构图或组件分区说明。
- 如果落代码，则对应组件布局切换规则。


### BL-BRAND-01 · 应用图标设计与资源接入

**目标**

- 为 DayPalette 建立一个与产品气质一致、可在商店与桌面上被快速识别的图标。

**方案设计**

- 图标不应走通用“调色盘 + 画笔”老套路径，而应从产品核心特征提炼：**三色关系、编辑感、纸片层叠、克制高级感**。
- 建议优先探索以下方向：
  - `三色叠片`：用 3 张有层次的色卡形成简化构图，对应 Hero 语言。
  - `DP 字母抽象`：把 `D / P` 融入三色关系中，但要避免做成互联网公司 Logo 风。
  - `单一符号 + 三色切面`：用一个简洁几何符号承载三色切分，强调高级、稳定、可缩放。
- 图标颜色应与应用本体一致：以中性浅底承接三色，而不是高饱和彩虹色；需要兼顾浅色桌面、深色桌面与商店缩略展示。
- 最终资源不仅要有设计稿，还要明确 HarmonyOS 图标资源切图与替换路径，避免设计定稿后落地断层。

**建议设计约束**

- 小尺寸下可读，不依赖复杂纹理与细字。
- 保持几何清晰，不使用过多渐变和装饰细节。
- 与启动图、商店截图、应用名形成统一识别系统。

**交付物**

- 2～3 个图标方向草案。
- 定稿图标的设计说明。
- HarmonyOS 资源替换清单与接入说明。


### BL-BRAND-02 · 应用名称重新确定与文案对齐

**目标**

- 在上架前收敛一个稳定、可传播、适合商店检索与品牌延展的最终名称，避免“文档名、包名、图标文案、商店名”各写各的。

**方案设计**

- 先明确命名约束，而不是直接拍脑袋定名。建议同时从这 4 个维度评估：
  - `识别性`：名称是否容易记住，是否能和“配色 / 今日 / 穿搭灵感”建立明确联想。
  - `气质一致性`：是否符合当前产品的高级、克制、编辑感，而不是工具箱或社区产品语气。
  - `双语一致性`：中文名与英文名是否能自然对应，避免中文很诗意、英文很工具化，或反过来。
  - `上架可用性`：是否过于通用、是否容易与现有产品撞名、是否适合商店搜索与截图展示。
- 建议按“三档方案”推进：
  - `保守档`：保留“今日配色 / DayPalette”主轴，只做微调。
  - `优化档`：在保留“今日 / 配色”语义的同时增强品牌感。
  - `品牌档`：允许中文与英文不做直译，但必须保证情绪气质统一。
- 名称一旦定稿，需要同步检查这些触点：
  - 应用内 `app_name`、关于页、设置页标题。
  - PRD、任务文档、发布文档、商店素材文案。
  - 图标展示名、启动图、截图标题、商店简介首句。
- 若最终决定更名，还应确认是否只改“展示名称”，还是连英文品牌名一起收敛；`bundleName` 原则上不在本轮轻易变更，除非明确需要重新定义应用身份。

**建议产出方式**

- 先列出 3～5 组候选中英文名称。
- 对每组名称补一句“品牌语气说明”和“为什么适合这个产品”。
- 评审后保留 1 组主方案 + 1 组备选，不要无限发散。

**交付物**

- 一份候选命名清单与筛选结论。
- 最终中英文名称及使用规范。
- 一份需要同步修改的文案 / 资源触点清单。
